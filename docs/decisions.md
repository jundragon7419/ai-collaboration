- 2026-11-16: 설정의 첫 질문은 협업 흐름이다. "기획 → 코더 → 리뷰어" 또는 "기획 → 코더 → 테스터 → 리뷰어"
- 2026-11-16: 테스터 역할을 추가한다. 테스터는 계획과 diff만 받고(코더 설명은 받지 않음) 테스트를 작성하며, 지정한 테스트 경로(기본 `tests/`)에만 쓸 수 있다. 테스트 실행은 테스터가 아니라 검사 명령이 한다. 테스트가 실패하면 코드와 테스트 중 무엇이 틀렸는지는 리뷰어가 판단하고, 갈리면 사람에게 넘긴다. 테스터는 첫 번째 쓰기 권한 추가 역할이다
- 2026-11-16: 검사 명령은 켜고 끌 수 있다. 기본은 켜짐이고, 끄면 결과와 PR에 "검사 미실행"을 표시한다. 테스터 흐름에서는 끌 수 없다. 저장소 종류별 후보(Python, JavaScript와 TypeScript, C와 C++, Java, Go, Rust)에서 고르거나 직접 입력한다. 끝나지 않는 명령, 파일을 고치는 명령, 설치나 네트워크가 필요한 명령은 검사로 쓸 수 없다
- 2026-11-16: 리뷰 차단 등급은 P0부터 P5까지이고, 고른 등급까지 차단한다. 권장은 P2까지. P0 보안 경계 위반, 데이터 손실, 비밀 유출 / P1 주된 기능 실패, 완료 조건 미충족 / P2 특정 조건에서 기능 실패, 바뀐 동작에 테스트 없음 / P3 사용자 영향이 작은 결함 / P4 유지보수 문제 / P5 사소한 것. 취향 차이는 어느 등급에도 넣지 않는다
- 2026-11-16: patch 결과 형태는 없앤다. 결과는 항상 로컬 브랜치 `aicollab/<run_id>`에 오케스트레이터가 사용자 이름으로 커밋한다. 공개 방식은 "확인 후 push"가 기본이고, "확인 후 push + Draft PR 생성"을 고를 수 있다. merge는 도구가 하지 않는다
- 2026-11-17: D01 구현 언어는 Python
- 2026-11-17: D06 위협 모델은 trusted-local. 본인 저장소에서 AI의 실수를 막는 것이 목적이다. 권한 옵션과 도구 제한을 적용하고, 범위 밖 변경은 실행 뒤 탐지해 중단한다. 악의적 저장소와 prompt injection 방어는 보장 대상이 아니다
- 2026-11-17: D07 기획자와 코더는 각각 한 명. 리뷰어 여러 명은 지원한다
- 2026-11-17: D09 원본에 미커밋 변경이 있으면 경고하고 고정 HEAD에서 시작한다. 미커밋 변경은 run에 들어가지 않는다
- 2026-11-17: D10 검사 명령은 저장소 종류별 후보를 기본으로 하고, 직접 입력한 명령은 doctor에서 한 번 시험 실행해 시간 안에 끝나는지와 파일을 바꾸지 않는지 확인한다
- 2026-11-17: D08 Windows에서는 실행 파일을 직접 실행한다. `npm`, `npx`는 `.cmd` 대신 node로 npm 스크립트를 직접 실행하고, `gradlew`, `mvn`처럼 대체할 수 없는 wrapper만 고정 인자로 `cmd /d /s /c` 실행을 허용한다
- 2026-11-17: D05 저장소에 의존성 준비 명령(`uv sync`, `npm ci` 등)을 등록하고, 작업 공간을 만든 직후 코더보다 먼저 오케스트레이터가 실행한다. 네트워크는 이 준비 단계에서만 허용하고 검사 단계에서는 막는다
- 2026-11-17: D11 저장소의 Git hooks는 평소처럼 실행한다. 비밀번호 입력 같은 사람 개입이 필요한 서명이 설정되어 있으면 커밋 전에 중단하고 알린다
- 2026-11-17: 변경이 없는 성공 run은 커밋과 push를 하지 않고 "변경 없음"으로 끝낸다 (common-docs D03의 empty commit 기술은 사용자 결정이 아님)
- 2026-11-17: D12 prepare는 기존 lock을 유지한다. lock이 없거나 manifest와 맞지 않으면 중단한다. doctor가 lock이 없는 저장소를 미리 알리고, 사용자가 run 밖에서 한 번 lock을 만들도록 안내한다(`uv lock`, `npm install` 등). run 안에서는 lock이 바뀌지 않는다
- 2026-11-17: D13 MVP는 구현 중 의존성이 바뀌어도 자동으로 다시 준비하지 않고 중단한다. 기획자는 계획에 "새 의존성 필요 여부"를 적고, 필요하면 승인 단계에서 사람에게 보인다. 사람은 의존성을 먼저 추가한 뒤 다시 시작한다. 코더가 계획에 없던 manifest나 lock을 바꾸면 중단한다
